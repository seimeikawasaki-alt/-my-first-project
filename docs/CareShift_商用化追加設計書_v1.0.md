# CareShift 商用化 追加設計書 v1.0

作成日: 2026-07-10
対象: CareShift(現行 v1.0 / React + Express + Prisma + PostgreSQL)
目的: 現行MVPを商用SaaSレベルへ引き上げるための追加・変更設計

---

## 0. 本設計書の位置づけと方針

### 0.1 現状評価サマリ

| 領域 | 現状 | 商用レベルとの差 |
|---|---|---|
| シフト自動生成 | 夜勤明けルール・連勤上限・公平分配・ペアリング制約まで実装済 | ◎ ほぼ流用可。制約に「配置基準」を追加する |
| 勤怠 | 打刻・修正・36協定残業上限管理 | △ 打刻手段がPCブラウザのみ。変形労働時間制なし |
| 給与 | 手当集計・明細PDF・全銀出力 | ✕ 控除(社保・税)なし。全銀は自前実行リスク大 |
| 介護特化機能 | 夜勤ルールのみ | ✕ 配置基準・常勤換算・加算・勤務形態一覧表なし |
| テナント構造 | 1施設1インスタンス(FACILITY_NAME環境変数) | ✕ マルチテナント・複数事業所非対応 |
| モバイル | レスポンシブのみ | ✕ PWA・プッシュ通知・GPS打刻なし |
| 帳票 | 給与明細のみ | ✕ 法定三帳簿・有給管理簿・勤務形態一覧表なし |

### 0.2 商用化の基本方針(3原則)

1. **「介護でしか作れない機能」を中核に据える**
   人員配置基準チェック(常勤換算)・勤務形態一覧表(参考様式)自動生成・加算要件チェック・処遇改善加算の配分管理。汎用勤怠SaaSにもカイポケにも「シフト作成と一体で」は提供されていない部分で勝つ。

2. **規制の重い領域は「連携」に委ねる**
   所得税・住民税・社会保険料・年末調整・銀行振込は自前実装しない。CareShiftは「勤怠実績と手当の確定データ」を作る役に徹し、freee人事労務・マネーフォワード給与・ジョブカン給与へCSV/APIで渡す。現行の全銀フォーマット出力機能は本番導線から外し、給与ソフト側の振込機能に委譲する。

3. **制度改定を前提にした「マスタ駆動」設計**
   配置基準・加算率・処遇改善加算の要件は介護報酬改定(3年ごと)で変わる。数値・条件はコードに埋め込まず、バージョン付きマスタデータ(適用開始日つき)として持ち、改定時はマスタ更新のみで対応できる構造にする。

### 0.3 想定ターゲット(本設計の前提)

- 第一ターゲット: 施設系介護(特養・老健・GH・有料/サ高住)+ 通所系。1法人1〜10事業所の中小法人
- 第二ターゲット: 障害福祉(GH・生活介護・放課後等デイ)— 配置基準エンジンをマスタ差し替えで転用
- 提供形態: マルチテナント型クラウドSaaS(1事業所あたり月額定額)

## 1. 全体アーキテクチャ変更

### 1.1 テナントモデル(最重要変更)

現行の「User直下にGroup」構造を、法人→事業所→ユニットの3階層に変更する。

```
Tenant(契約=法人)
 └─ Corporation情報・課金プラン
     └─ Office(事業所) ×N   ← 指定サービス種別・定員・営業日を持つ
         └─ Unit(ユニット/フロア=現行Group) ×N
             └─ StaffAssignment(職員の所属・職種・常勤区分)
```

ポイント:
- 職員(User)はテナント配下に1レコード。**複数事業所への兼務**を `StaffAssignment` の複数行で表現する(常勤換算計算に必須。兼務者の按分は介護の実地指導で必ず見られる)
- すべての業務テーブルに `tenantId` を付与し、Prisma Client Extension(`$extends`)で全クエリに `tenantId` フィルタを強制注入する。加えてPostgreSQLのRow Level Securityを二重防壁として有効化
- 現行の環境変数 `FACILITY_NAME` は `Office.name` に移行

### 1.2 権限モデル(RBAC再設計)

| ロール | スコープ | 主な権限 |
|---|---|---|
| VENDOR_ADMIN | 全テナント | 運営者。テナント管理・マスタ配信 |
| CORP_ADMIN | 法人 | 全事業所の閲覧・設定・給与確定・処遇改善計画 |
| OFFICE_ADMIN | 事業所 | シフト作成・勤怠修正・帳票出力(現行ADMIN相当) |
| LEADER | ユニット | 自ユニットのシフト調整・交代承認 |
| STAFF | 本人 | 打刻・希望提出・自分の明細/シフト閲覧(現行STAFF相当) |

JWT クレームに `tenantId / officeIds / role` を含め、ミドルウェアで `requireRole(role, scope)` を一元化する。現行の `ADMIN/STAFF` 2値ロールからの移行マイグレーションを用意する。

### 1.3 インフラ・運用(非機能)

- 構成: フロント=静的ホスティング(CloudFront等) / API=コンテナ(ECS/Fargate等、水平スケール可) / DB=マネージドPostgreSQL(Multi-AZ)
- バックアップ: PITR + 日次スナップショット35日保持。RPO 5分 / RTO 4時間を目標
- 監視: 死活・エラーレート・p95レイテンシ・ジョブ失敗のアラート(現行 `/api/health` を拡張し依存先チェックを追加)
- セキュリティ: 通信TLS必須、保存時暗号化、監査ログ(実装済のAuditLogを全書き込み系APIに拡大)、IP制限オプション、パスワードポリシーは現行踏襲+管理者ロールに多要素認証(TOTP)を追加
- ガイドライン対応: 医療情報システム関連の「3省2ガイドライン」相当の安全管理措置をチェックリスト化し、営業資料に添付できる状態にする
- 個人番号(マイナンバー)は**保持しない**(給与ソフト側で管理)。設計上の取扱範囲を明文化する

## 2. 中核新機能A: 人員配置基準・常勤換算エンジン

介護特化の存在理由となる機能。シフト画面・自動生成・帳票のすべてがこのエンジンの上に載る。

### 2.1 常勤換算の計算仕様

```
常勤換算数(FTE) = Σ(各職員の対象期間の勤務予定/実績時間) ÷ 事業所の常勤勤務時間

- 事業所の常勤勤務時間: Office.fullTimeWeeklyHours(既定40、下限32)
- 期間: 暦月(予定ベース=シフト / 実績ベース=勤怠 の両方を算出)
- 兼務者: StaffAssignmentの職種・事業所ごとに勤務時間を按分
- 職種(JobCategory): 介護職員 / 看護職員 / 生活相談員 / 機能訓練指導員 /
  介護支援専門員 / 管理者 / サービス提供責任者 / その他(マスタで拡張可)
```

### 2.2 配置基準ルールのデータモデル(マスタ駆動)

```prisma
model ServiceType {            // 指定サービス種別(特養/老健/GH/通所介護/訪問介護/障害系…)
  id            String  @id @default(cuid())
  code          String  @unique   // 例: "TOKUYO", "DAYCARE"
  name          String
  insuranceKind InsuranceKind     // KAIGO / SHOGAI
}

model StaffingRule {           // 配置基準ルール(改定でバージョンが増える)
  id             String   @id @default(cuid())
  serviceTypeId  String
  name           String            // 例: "介護・看護職員 3:1"
  ruleKind       RuleKind          // RATIO(利用者比) / MIN_COUNT(最低人数) /
                                   // NIGHT_MIN(夜勤帯最低配置) / FULLTIME_REQUIRED(常勤要件)
  jobCategories  String[]          // 対象職種コード
  params         Json              // 例: {"ratio":3} / {"min":1,"perUnit":true} /
                                   // {"bands":[{"maxUsers":25,"min":1},{"maxUsers":60,"min":2}]}
  timeWindow     Json?             // 夜勤帯等 {"from":"22:00","to":"07:00"}
  effectiveFrom  DateTime          // 適用開始日(報酬改定対応)
  effectiveTo    DateTime?
  source         String?           // 根拠(省令条文等のメモ)
}

model Office {                 // 事業所に定員・利用者数を持たせる
  ...
  serviceTypeId        String
  capacity             Int      // 定員
  avgUsers             Int?     // 前年度平均利用者数(比率計算の分母に使用)
  fullTimeWeeklyHours  Int @default(40)
}
```

> 注意: 配置基準の具体値(3:1、夜勤帯の人数バンド等)は**シードデータとして2024年度改定ベースの参考値を投入するが、リリース前に必ず最新の厚労省令・自治体の指定基準と照合する**こと。本設計はあくまで「任意のルールを表現できる器」を定義する。

### 2.3 チェックエンジンの動作

```
入力: 対象月のシフト(予定) or 勤怠(実績) + Officeの利用者数 + StaffingRule[]
処理: 日別・時間帯別に職種ごとの在籍数/常勤換算数を集計し、各ルールを評価
出力: ComplianceReport {
  officeId, month, basis: "PLAN" | "ACTUAL",
  dailyResults: [{ date, ruleId, required, actual, status: OK|WARN|NG }],
  monthlyFte: [{ jobCategory, requiredFte, actualFte, status }],
  violations: [...]  // シフト画面・生成エンジン・帳票が共通で参照
}
```

組込みポイント:
1. **シフトグリッド画面**: 各日の列ヘッダ直下に「配置充足バー」(緑/黄/赤)を常時表示。クリックで不足内訳(どの職種が何人/何FTE不足か)をポップオーバー表示
2. **自動生成エンジン**: 既存 `shiftGenerator.service.ts` の制約評価に `StaffingRule` 充足を最優先ハード制約として追加。既存のWarning型に `STAFFING_VIOLATION` を追加
3. **保存時ガード**: NGのままシフト確定しようとした場合は理由入力を必須にして監査ログへ記録(ブロックはしない=現場の実情優先)

### 2.4 勤務形態一覧表(参考様式第1号)の自動出力 ★差別化の目玉

指定申請・運営指導(実地指導)で必ず提出を求められる帳票。シフトデータから自動生成できるのはシフト管理ツールならではの強みで、営業上の「刺さる一言」になる。

- 出力単位: 事業所 × 月 × 職種
- 内容: 職員ごとの日別勤務時間(シフト記号ではなく時間数)、週平均勤務時間、常勤換算数の自動計算行
- 形式: Excel(xlsx)とPDF。自治体によって微妙に様式が異なるため、列マッピングをテンプレート化して差し替え可能にする
- 実装: 既存の `shiftPrint.service.ts` を汎用帳票サービス `reporting.service.ts` に発展させる

## 3. 中核新機能B: 加算要件チェックと処遇改善加算

### 3.1 加算要件チェック(第1段階: シフト連動系のみ)

全加算を網羅しようとしない。**シフト・勤怠データから機械的に判定できる加算**に限定して価値を出す。

| 加算例 | 判定に使うデータ | 判定内容 |
|---|---|---|
| 夜勤職員配置加算 | 夜勤帯シフト | 基準+1名以上の夜勤配置が月を通じて維持されているか |
| サービス提供体制強化加算 | 職員マスタ(資格・勤続年数) | 介護福祉士の割合・常勤職員割合・勤続年数割合 |
| 特定事業所加算(訪問系) | 資格・研修記録 | 有資格者割合等 |

データモデルは `StaffingRule` と同じ思想で `AdditionRule`(params Json + effectiveFrom)を定義し、判定結果を月次 `AdditionComplianceReport` として保存。ダッシュボードに「今月の加算充足状況」カードを追加する。既存の `Qualification / StaffQualification` モデルがそのまま資格割合の分子に使える。

### 3.2 処遇改善加算(介護職員等処遇改善加算)の配分管理

給与機能を「介護特化」たらしめる機能。税計算をしない方針でも、ここはCareShiftが担うべき領域。

```prisma
model TreatmentImprovementPlan {   // 年度計画
  id              String @id @default(cuid())
  tenantId        String
  fiscalYear      Int
  additionTier    String          // 加算区分(Ⅰ〜Ⅳ等。マスタ参照)
  estimatedAmount Int             // 加算見込額(年)
  policy          Json            // 配分方針(ベア/手当/一時金の比率、対象職種)
}

model TreatmentImprovementAllocation { // 職員×月の配分実績
  id        String @id @default(cuid())
  planId    String
  userId    String
  yearMonth String                // "2026-07"
  method    AllocationMethod      // BASE_UP / MONTHLY_ALLOWANCE / BONUS
  amount    Int
  payrollDetailId String?         // 給与明細行との紐付け
}
```

機能:
1. 配分シミュレーション: 加算見込額を対象職員に按分し、月額手当案を自動提示(勤務時間比・職種係数で配分)
2. 給与項目への自動反映: 既存 `SalaryItem` に `treatmentImprovementFlag` を追加し、明細上で処遇改善原資由来の支給を区別
3. **実績報告書用の集計出力**: 年度末に「加算総額 vs 賃金改善実績額」の突合表をExcel出力(様式は自治体差があるためテンプレート方式)

## 4. 給与の再設計: 「計算完結」から「確定データのハブ」へ

### 4.1 スコープの再定義

| 項目 | CareShiftが担う | 外部給与ソフトが担う |
|---|---|---|
| 勤怠集計(所定/残業/深夜/休日/夜勤回数) | ● | |
| 介護特有手当(夜勤手当・処遇改善・資格手当) | ● | |
| 総支給額(課税/非課税区分つき) | ● | |
| 社会保険料・雇用保険・所得税・住民税 | | ● |
| 年末調整・法定調書 | | ● |
| 銀行振込(全銀) | | ● |

既存の `payroll.calc.ts`(端数処理・時給/月給・割増計算)はそのまま「支給側エンジン」として活かす。既存の全銀実装(`zengin.ts`)は削除せず、`ExperimentalFeature` フラグ配下に隔離し既定OFFとする。

### 4.2 連携方式

- **CSVエクスポート(Phase B)**: 勤怠データ形式と給与データ形式の2種。主要3社(freee人事労務 / マネーフォワード給与 / ジョブカン給与)+汎用形式のアダプタをテンプレート化(`ExportTemplate` マスタ: 列名・日付書式・丸めルールをJSON定義。ユーザーがマッピングを編集可能)
- **APIコネクタ(Phase D)**: freee人事労務APIへの勤怠・支給項目の直接連携(OAuth2)。他社は需要を見て追加
- 逆方向: 職員マスタのCSVインポート(既存介護ソフト・給与ソフトからの移行導線)

## 5. 労働法対応の強化

### 5.1 1ヶ月単位の変形労働時間制(シフト制介護施設の標準)

```prisma
model WorkTimeSystem {
  id            String @id @default(cuid())
  officeId      String
  kind          WorkTimeKind   // STANDARD / MONTHLY_FLEX(1ヶ月単位変形)
  closingDay    Int            // 締め日
  effectiveFrom DateTime
}
```

- 月の法定労働時間枠 = 40 × 暦日数 ÷ 7 (28日=160.0h / 30日=171.4h / 31日=177.1h)
- シフト作成時: 職員ごとの月間予定労働時間が枠を超えるとWARN表示(自動生成のソフト制約にも追加)
- 割増計算: 変形制では「日8h超」ではなく「シフト所定超+月枠超」で残業を判定するよう `payroll.calc.ts` の残業判定を分岐(既存の勤怠種別所定時間ロジックを拡張)

### 5.2 有給5日取得義務・その他

- 既存 `PaidLeaveGrant/Usage` に「基準日から1年で5日未取得」アラートを追加(ダッシュボード+管理者通知)。年次有給休暇管理簿の帳票出力
- 勤務間インターバル(11時間)チェックをオプション設定として追加(夜勤明け→日勤のような危険パターン検知。既存 `shiftRules.calc.ts` の `projectNightRest` を拡張)

### 5.3 法定帳票の追加

`reporting.service.ts` に集約: 出勤簿(職員×月) / 賃金台帳(職員×年度) / 労働者名簿 / 年次有給休暇管理簿 / 勤務形態一覧表(§2.4) / 36協定超過状況レポート(既存OvertimeMonthlyStatsを帳票化)。すべてPDF+Excel。

## 6. モバイル体験(スタッフ向けPWA)と打刻の拡張

### 6.1 方針

ネイティブアプリは作らない。現行のReactフロントを**PWA化**(インストール可能・オフライン耐性・プッシュ通知)し、スタッフ向け画面をモバイルファーストで再設計する。ストア審査・二重開発を避けつつ、体験は「アプリ」に近づける。

### 6.2 スタッフPWAの画面構成(再設計)

```
[ホーム]     今日のシフト / 打刻ボタン(大) / 未読通知 / 今月サマリー
[シフト]     月カレンダー(自分+同ユニットの当日メンバー表示)
[希望提出]   希望休・希望シフトのタップ入力(締切カウントダウン表示)
[申請]       シフト交代 / 残業 / 有給 / 打刻修正 — ステータス追跡
[給与]       明細一覧・PDF(既存機能をモバイル最適化)
```

### 6.3 打刻手段の拡張

| 手段 | 対象 | 実装 |
|---|---|---|
| スマホ打刻+GPS | 訪問系・直行直帰 | Geolocation APIで座標記録。事業所/利用者宅からの距離をサーバ側検証(閾値はOffice設定)。位置情報の取得は同意画面必須 |
| 共有タブレット+QR | 施設系 | 事業所に掲示するQR(TOTPで60秒ローテーション)をスタッフ端末で読取り→なりすまし打刻防止 |
| ICカード(FeliCa IDm) | 施設系オプション | Phase C以降。市販PaSoRi+常設端末のWebUSB読取 |

打刻レコードに `method / lat / lng / deviceId` を追加し、勤怠一覧で打刻手段・位置の妥当性をアイコン表示する。

### 6.4 通知基盤

`Notification` モデル+配信チャネル抽象化(Web Push / メール / LINE公式アカウント連携はPhase D)。トリガー: シフト公開・変更 / 交代依頼・承認 / 希望提出締切前日 / 打刻漏れ / 有給5日アラート / 36協定接近。ユーザーごとにチャネルと種別のON/OFF設定を持つ。

- 公開REST API(APIキー+スコープ)を `/api/v1/external/` に用意: 職員マスタ取得/更新、シフト取得、勤怠実績取得

## 8. UI/UXデザイン刷新

### 8.1 デザインシステム(トークン定義)

現行Tailwind構成を活かし、`tailwind.config.js` にトークンを集約する。

```
カラー:
  primary:   teal-600 (#0D9488)  … 医療・介護の信頼感。現行の青系から変更
  secondary: amber-500            … 注意・希望休
  danger:    rose-600             … 配置基準NG・打刻漏れ
  night:     indigo-700           … 夜勤(シフトグリッドで最重要の識別色)
  surface:   slate-50 / white、境界 slate-200

タイポグラフィ: "Noto Sans JP" / 数字は "Inter"(表の桁揃え用に tabular-nums)
密度: 管理画面はコンパクト(行高36px)、スタッフPWAはゆったり(タップ領域44px+)
アクセシビリティ: コントラスト比4.5:1以上、シフト種別は色+記号の二重符号化
             (色覚多様性対応。介護現場は50-60代の利用者も多い前提でフォント基準16px)
```

### 8.2 管理画面の主要リデザイン

1. **シフトグリッド(最重要画面)**
   - 上段固定行に日別「配置充足バー」(§2.3)。不足日は列全体を薄い赤背景に
   - 右パネル: 選択職員の月間サマリー(勤務日数/夜勤回数/連勤/残業見込/月枠残)
   - セルはドラッグ&ドロップ+キーボード入力(現行の操作性を維持)。Undo/Redo追加
   - 表示切替: 職員×日 / 職種×日(配置基準ビュー) / ユニット別
2. **ダッシュボード**: 「今日の出勤状況」(既存)に「配置基準ステータス」「加算充足」「有給5日アラート」「36協定接近者」のカードを追加。法人管理者には事業所横断ビュー
3. **サイドバー再編**: シフト / 勤怠 / 給与 / コンプライアンス(配置基準・加算・帳票) / 職員 / 設定 の6グループに整理(現行はフラットに項目が並び過ぎ)

### 8.3 情報設計の原則

- 管理者の1日の動線(朝: 出勤確認 → 日中: 申請処理 → 月次: シフト作成・給与)に沿って上から並べる
- 「NGを出さない」より「NGの理由と直し方を示す」— 違反表示には必ず「この日に◯◯(職種)をあと1名」という解決アクションを添える

## 12. リスクと対応

| リスク | 対応 |
|---|---|
| 配置基準・加算の解釈が自治体で異なる | ルールをマスタ駆動+テンプレート化(§0.2)。帳票様式も差し替え可能に。免責として「最終確認は事業所責任」をUI上に明記 |
| 報酬改定(次回2027年度)で要件変更 | effectiveFrom/To付きマスタで新旧併存。改定対応をサブスク価値として訴求 |
| 給与連携先の仕様変更 | ExportTemplateをユーザー編集可能にし、公式テンプレは運営が配信更新 |
| 全銀・税計算への期待とのギャップ | 営業資料で役割分担(§4.1表)を先に提示。「給与ソフトの置き換えではなく前工程の自動化」と位置づける |
| 個人情報(位置情報・給与) | 位置情報は打刻時のみ取得・同意必須・保持期間設定。プライバシーポリシー整備 |
